Study Quizzes: architecture and how the parts work together

How samolkhoeurn.github.io/quiz is built, what happens step by step when a student takes a quiz or you edit a question, where the limits are, and the sizes it can grow to. Updated for the question manager, KaTeX typesetting, the English interface and the six subjects.

1. The system map

There is still no server of your own. Everything runs in the browser, which downloads the app from GitHub Pages, typesets maths with a library from a public CDN, and talks directly to two Google Firebase services: Authentication for logins and Firestore for data. Questions have two homes: the files in git (the master copy, which I write and validate) and, for chapters you have edited online, a document in Firestore that takes precedence.

2. How the pieces work together

Two flows cover almost everything that happens: a student taking a quiz, and you changing a question. Both are sequences of small calls from the browser; no step waits on a server of yours.

4. Three sizes it can grow to

Tier 1, today done

Six subjects (four Khmer MoEYS subjects, Australian Year 9 and Year 2 maths), per-student chapter permissions and interface language, timed quizzes with random draws and weighted 100-point scoring, reports with per-question timing, and the online question manager with hit rates and file export.

Tier 2, a tutoring group 1–2 days

A role field so other teachers can be invited and see only their own students; a summary document per student so reports stay cheap as history grows; one Cloud Function for password resets and creating many accounts from a list. Cloud Functions need the Blaze plan (pay-as-you-go with the same free allowances), so the realistic bill stays near zero.

Tier 3, a school or a product several weeks

Answer keys move off the client: a Cloud Function hands out a drawn set of questions without the a field, receives the answers and grades them. Questions move to one document each for cross-chapter search and per-question statistics at scale. Data gains organisation and class levels, and a custom domain, terms of use and child-data protection become real obligations.

Stable contracts. The question format {lv, q, o, a, ex} and the attempt record (answers[] with chosen, correct, pts, ms) are the same in the files, in Firestore and in every report, and are designed to survive all three tiers. Keep them stable and today's history and content remain usable whatever the site becomes.

5. Worth doing soon at any size

  • Custom domain: a CNAME in the repository plus DNS records; add the domain under Firebase Authentication → Authorized domains.
  • Backups: a monthly Firestore export from the console, or a "download all attempts as CSV" button on the admin screen.
  • Use the hit rates: after a few hundred attempts, re-label easy/medium/hard from evidence and rewrite the questions everyone misses; the question manager now makes this a five-minute job.
  • Content review: a Cambodian teacher reading each Khmer chapter once would catch terminology that a validator cannot; corrections can be made directly in the manager.
