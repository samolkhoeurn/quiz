Khmer Quiz: architecture and where it can grow

How samolkhoeurn.github.io/quiz is built today, what each part can carry, and the three realistic sizes it could grow to without rewriting what already works.

1. What runs today

There is no server of your own. The browser does all the work: it downloads static files from GitHub Pages, talks directly to two Google Firebase services for identity and data, and stores results there. Nothing in the middle can go down independently of Google or GitHub.

2. Where the limits actually are

For one family the free tiers are effectively unlimited: a quiz is one write and a report is a few dozen reads. The ceilings that matter appear only if the site becomes a product for many students or a school. Here is where each part starts to strain, and whether it is a real wall or just a setting.

3. Three sizes it could grow to

Each tier keeps everything from the one before. The question content, the static site, and the attempt format stay the same throughout, so moving up is adding boxes, not replacing them.

Tier 1, today: one admin, a handful of students done

Exactly what is deployed. Suitable for your nephew and perhaps a few cousins. The two conveniences you will feel first are account administration (no password reset without a server) and the single hard-coded admin e-mail.

Tier 2, a tutoring group: several teachers, up to about a hundred students 1–2 days of work

Three additions, all inside Firebase, none of which change the quiz itself. First, a role field on each users document (admin, teacher, student) and rules that read it, so you can invite other teachers and let each teacher see only their own students. Second, a summary/{uid} document that the app updates on every submit (best and last score per chapter, totals), so the reports screen reads one small document instead of every attempt; this is what keeps read counts, and therefore cost, flat as history grows. Third, one small Cloud Function with the Firebase Admin SDK, giving the admin screen "reset password", "create 30 students from a list" and "delete account". Cloud Functions need the Blaze plan, which is pay-as-you-go with the same free allowances, so the realistic bill stays at zero to a few dollars.

Tier 3, a school or a product: many classes, graded tests several weeks

This is the point where the architecture changes shape rather than grows. Answer keys move off the client: a Cloud Function hands the browser a drawn set of questions without the a field, receives the answers, grades them, and writes the attempt itself, so a student cannot read the key from the page source. Question banks move from git files into Firestore (or a headless CMS) so teachers can add and review questions in a form instead of editing JavaScript, with the validator running server-side on save. Data gains a hierarchy of organisation, class and student for isolation and billing, and you would add proper analytics (which questions are missed most, difficulty calibration from real results). At this tier a custom domain, terms of use and data protection for minors become real obligations too.

What not to change. The attempt document format (answers[] with chosen, correct, points and milliseconds per question) and the bank format ({lv, q, o, a, ex}) have been designed to survive all three tiers. Keep them stable and every report, export or analysis you build later works on the history you are collecting now.

4. Things worth doing soon regardless of tier

  • Custom domain (e.g. khmerquiz.com): a CNAME in the repository plus four DNS records; GitHub issues the HTTPS certificate. Remember to add the domain under Firebase Authentication → Authorized domains.
  • Backups of results. Firestore has no automatic export on the free plan. A monthly export from the console, or a one-click "download all attempts as CSV" button on the admin screen, protects the history.
  • Analytics on the questions. With a few hundred attempts you can compute each question's actual hit rate and re-label the easy/medium/hard levels from evidence rather than judgement. The data is already there in attempts.
  • Content review workflow. The banks were written from the textbooks and machine-checked; a Cambodian teacher reading each bank once would catch terminology that a validator cannot. BANK_SPEC.md and validate.mjs make that review and any additions mechanical.
  • Keep firebase-config.js honest. It is public by design (security lives in the rules), but the admin e-mail must match in three places: the config, the rules, and Authentication → Users.
